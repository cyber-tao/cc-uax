# cc-uax report contract

Read this reference when interpreting `asset` or `project` JSON.

## Completion fields

- `schema_version`: Version of the report contract, independent from the CLI version. Asset reports use schema version `6`; project reports use schema version `7`.
- `status`: `complete`, `partial`, or `unsupported` for the requested analysis scope.
- Asset reports expose `coverage` counters for exports, properties, EdGraph, RigVM, PCG, StateTree, opaque regions, and diagnostics within the requested view. Byte conservation over export payloads is reported by `export_bytes_total` (sum of analyzed `serial_size`) and `unclassified_bytes`, which is always `0` in a correct report — a non-zero value is a defect.
- `coverage` distinguishes the two kinds of gap it can report, because on a real project one dwarfs the other. Of `opaque_bytes`, `class_payload_bytes` is export tails a class's own serializer wrote (mesh render data, lightmaps, compiled bytecode) and `unattributed_tail_bytes` is tails after a tagged-property block that did not close cleanly — the second is the one to watch when judging decoder coverage. Incomplete tagged-property exports split the same way: `property_exports_not_tagged` is a payload shape the decoder does not model, `property_exports_failed` is a tagged block that broke partway.
- Project reports expose sanitized `layout`/`mounts`, filesystem/index accounting in `stats`, generated runtime/resource `reachability`, and semantic accounting in aggregate `analysis` (`assets`, `complete_assets`, `partial_assets`, `unsupported_assets`, `scan_failures`, and summed `coverage`). `stats.failed` counts only asset-level failures (a discovered asset that failed to read, parse, or index), so `discovered == indexed + failed + skipped` holds; infrastructure failures (mount/discovery/ownership/cache) are reported in `failures` and counted in `analysis.scan_failures`, not in `stats.failed`. Symbolic links are not followed; each skipped link is counted in `stats.skipped_symlinks` and surfaced as a `discovery` diagnostic.
- `stats` always emits every counter, including zeros: `discovered`, `indexed`, `failed`, `skipped`, `skipped_symlinks`, `external_actors`, `external_objects`, `owned_external_packages`, `unowned_external_packages`, `cache_hits`, `cache_misses`, `cached_parse_failures`. `cache_hits` counts entries actually reused, so a fresh entry that still needed a re-read is a miss.
- Each inventory entry reports its package's `file_version_ue5`, and aggregate `analysis.file_versions` is the per-version package count for the whole scan. That distribution is the only statement of which UE version gates a scan actually exercised: a report covering one version says nothing about the others, however complete it looks.
- Aggregate `analysis` also publishes three integrity numbers so they can be checked without walking the inventory: `partial_assets_without_explanation`, which is `0` in a correct report because a partial status must name its gap, and `grouped_opaque_regions`/`grouped_opaque_bytes`, which must equal `coverage.known_opaque_regions`/`coverage.opaque_bytes` — reporting both sides is what makes it verifiable that grouping lost no region.
- The sparseness rule below does not apply to `stats`, the aggregate `analysis` counts (`assets`, `complete_assets`, `partial_assets`, `unsupported_assets`, `scan_failures`, `partial_assets_without_explanation`, `grouped_opaque_regions`, `grouped_opaque_bytes`), `reachability.failed_assets` (a count, not a package set, despite sitting beside the set-valued reachability fields), or `mounts`. Those always emit every field, including zeros.
- Top-level project sections are `layout`, `mounts`, `entry_points`, `reachability`, `analysis`, `stats`, `inventory`, `forward`, `reverse`, `ownership_closure`, `failures`, `diagnostics`, and `focused`.
- `reachability` carries `configured_roots`, `reachable_runtime_packages`, `ownership_closure_members`, `unreachable_project_assets`, `isolated_project_assets`, `partial_packages`, `unsupported_packages`, and `failed_assets`. Each configured root carries a `resolution` of `indexed`, `referenced_only`, or `unresolved`: `resolved_package` alone does not prove the root exists in this scan, because reference targets outside every mount also canonicalize to a name.
- Cross-package references are carried once by the top-level `forward`/`reverse` adjacency maps; inventory items do not repeat them. Each project inventory item retains its own compact analysis status, coverage, capabilities, graph counts, diagnostics, and opaque accounting. Focused packages additionally appear under `focused` with their full typed analysis; a `--focus` pattern that matches nothing, or a focused package that fails to read or parse, is recorded as a `focus`-stage entry in `failures` rather than aborting the report. A focused package that the parser deliberately does not target is not a focus failure: its inventory entry already reports `status=unsupported`.
- A mapped package the parser deliberately does not target — a UE4 package (`FileVersionUE5` = 0), a cooked or unversioned package, a UE3 package, a big-endian console package, or a package-level-compressed package — is indexed as `unsupported` evidence with an `unsupported_reason`, counted in `analysis.unsupported_assets` and listed in `reachability.unsupported_packages`. It is not a scan failure and does not appear in `failures`. Its references are unknown, so it contributes no `forward` edges. Bytes that are not a readable package at all remain a `parse` failure.

Reports are **sparse**: empty and default-valued fields are omitted rather than emitted as `null`, `[]`, `false`, `""`, `"None"`, or `0`. A missing field therefore means the default value (no value, empty collection, `false`, or a zero count) — read it as absent, not as an error. `coverage` keeps its non-zero counters and always retains `bytes_total`, `exports_total`, and `exports_analyzed`; zero-valued counters are omitted. Sparseness applies to the typed report fields; a decoded property `value` (inside `exports[].properties` or a nested `@struct` block) is the exact serialized value and may be an explicit `null`, `""`, `[]`, or `"None"` when the asset stored one.

Pin `direction` and pin-type `container` render as plain strings (for example `"output"`, `"array"`); an out-of-range value renders as `{"unknown": <n>}`. Export byte placement (`object_flags`, `serial_offset`, `serial_size`, and the script-serialization range) is grouped under an optional `serialization` object emitted only in the `full` asset view; the focused `summary`/`logic`/`properties`/`references` views omit it.

Typed graph nodes and pins (PCG, RigVM, StateTree) carry distilled semantic fields plus their stable `index`; they do not repeat the raw tagged-property block. Read a node's full properties from the matching `exports[]` entry by `index`. StateTree task/condition `node_properties`/`instance_properties` and transition data remain on the typed node because they are distilled from nested arrays, not a whole export.

Counts describe the requested scope; they are not interchangeable. An indexed package is not necessarily semantically analyzed or complete.

## Focus selection

`--focus <PACKAGE_OR_GLOB>` selects packages by canonical path. A trailing asset/object suffix is stripped, matching is case-insensitive, `?` matches one non-separator character, `*` matches within a single path segment, and `**` matches across `/` separators (so `/Game/Blueprints/*` selects direct children and `/Game/Blueprints/**` selects the whole subtree).

## Output budgeting

`--max-output-bytes <N>` caps the rendered JSON at N UTF-8 bytes. Budgeting is a presentation concern: it never changes evidence. The top-level skeleton — `schema_version`, `status`, `summary`, `coverage`, `capabilities`, `diagnostics`, `known_opaque`, and (for projects) `reachability`, `stats`, `analysis`, `layout`, `mounts`, `entry_points` — is always preserved. Heavy detail is elided in a fixed priority order: tagged-property values, then pins, then graph elements (nodes/states/edges/links), then the large top-level sections (`exports`, graphs, `inventory`, `focused`, adjacency, `ownership_closure`), then large `reachability` package lists (keeping `configured_roots` and counts). Every large section, including the nested `reachability` lists, is first truncated to as many leading elements as the remaining budget allows before any section is dropped whole, so a tight budget still returns leading structural detail across sections; a truncated array keeps its leading entries followed by an `{"@elided": <count>}` marker, and a truncated object keeps its leading entries plus an `"@elided": <count>` key. A top-level `output` block records `truncated`, `budget_bytes`, `emitted_bytes`, and `elided` (each reduced section with its dropped-element count; section truncation is reported under `section_truncation`). A fully elided array or map is replaced by an `{"@elided": <count>}` marker; an elided tagged-property value is replaced by `{"@elided": "property value"}`.

Two limits are deliberate. The skeleton protection is **top-level only**: eliding `inventory` or `focused` also drops the per-asset `status`/`coverage`/`capabilities`/`diagnostics`/`known_opaque` nested inside them. And the skeleton is always emitted as valid JSON even when it alone exceeds the budget, so a very small `N` returns more than `N` bytes with `output.truncated=true` rather than invalid or evidence-stripped JSON. `output.emitted_bytes` can differ from the exact byte length by a few bytes, and the trailing newline is outside the budget. `output.truncated=true` means the report is size-reduced, not evidence-incomplete; re-query a narrower `--focus`/`--view` for the dropped detail.

## Evidence identities

Use package path plus adapter and graph/model identity as the namespace. Within it, use stable node/pin/state identifiers and explicit edges. Display names are labels, not identities.

K2/EdGraph edges have `kind=exec|data`. A gameplay path normally needs ordered exec edges plus the data edges/defaults that determine branch inputs, call parameters, spawn classes, or object targets. Intra-graph connectivity is carried once by the graph's `edges`; a pin's `linked_to` retains only cross-graph and unresolved connections (those a per-graph edge cannot express), so use `edges` for in-graph flow and `linked_to` only for links that leave the graph.

RigVM links store both source and target pin paths. Count each canonical model link once. StateTree transitions must retain source, target, trigger, conditions, and task ownership. PCG edges must retain source/target node and pin identities.

## Opaque and failure records

Every byte-backed unstructured region must include a capability/type, reason, and byte range. A capability-level opaque record may have no byte range when it describes several serialized regions. `known_opaque` preserves alignment but does not prove source logic. An `error` means the requested structure was not reliably decoded.

An asset report lists every opaque region individually in `known_opaque`, each with its `path`, `kind`, `type_name`, `reason`, and `byte_range` (`start`, `end`, `size`, `preview`). A project report aggregates instead: `inventory[].analysis.known_opaque` keeps the per-kind counts, a `bytes` total, and `groups` — one entry per distinct (`kind`, `type_name`, `reason`) with its `regions` count and `bytes` total. Group `regions` sum to `coverage.known_opaque_regions` and group `bytes` sum to `coverage.opaque_bytes`, so opaque bytes stay attributable; the per-region byte ranges and previews are what `cc-uax asset` and `--focus` attach in full. A single asset can carry thousands of regions of a handful of distinct kinds, which is why the project view groups them.

A `known_opaque` region whose reason says the legacy property tag does not record a set/map element struct name (diagnostic code `property_tag_missing_inner_struct_name`) is a limit of the on-disk format, not a decoder defect. Below `FileVersionUE5` 1012 a container tag records only the element's property type. `TArray` is the exception: `FArrayProperty::SerializeItem` writes a full inner `FPropertyTag` into the payload, so legacy struct arrays decode and report their element type. `FSetProperty` and `FMapProperty` write no such tag, leaving the `UScriptStruct` to UE's reflection registry.

Export tails are classified by cause. A tail after a property block that closed where it should is data the class's own `Serialize` override wrote and is expected; a tail after a block that did not close cleanly is unattributed. Compiled Blueprint bytecode and compiled Niagara VM/GPU payloads are named capabilities (`blueprint_bytecode`, `niagara_compiled`) alongside `rig_vm_bytecode` and `rig_hierarchy`.

An export whose payload is not a tagged-property block at all emits `export_payload_not_tagged` and is counted in `property_exports_not_tagged`. A `partial` report always carries either a diagnostic or a capability `detail` naming its gap, and `capabilities[].detail` survives into project inventory entries because it is the only field that says what is missing.

Never treat an empty diagnostics array alone as completeness. Check `status`, `coverage`, exact byte consumption, and `capabilities` together.

## Project graph

Project reports expose one inventory and bidirectional adjacency for all scanned mounts. The default mounts are `/Game` plus every plugin content root under `Plugins/`, mounted as `/{.uplugin base name}/` the way `FPluginManager` mounts them — which is often not the plugin's directory name. An explicit `--mount` adds to that set, or redirects a root it names.

`reachability.configured_roots` records config-derived package/class roots and, in `resolution`, whether each is an indexed asset, a name referenced from scanned assets but outside every mount, or unknown. Roots come from `GameMapsSettings` and from the `ProjectPackagingSettings` cook lists (`+MapsToCook`, `+DirectoriesToAlwaysCook`), because `GameDefaultMap` is frequently a developer map while the cook list is what a build actually ships; a cook directory expands to the indexed packages beneath it. A `Config/<Platform>/` directory is reported as a platform override only when its config actually changes an entry point. `reachability.reachable_runtime_packages` is computed from those roots, scanned references, and ownership closure; it is a runtime-reachability set, so it includes externally-referenced packages (engine, plugin, and `/Script/...` packages) that reachable assets depend on, not only project-owned packages. `reachability.ownership_closure_members` records World Partition external packages owned by their map, plus Level Instance / Packed Level Actor sub-levels whose `WorldAsset` / `PackedWorldAsset` was decoded on those actor classes. A LI/PLA world that is only present as a soft reference and was not attached to a host map's closure is reached through adjacency, not as a closure member.

`reachability.unreachable_project_assets` and `reachability.isolated_project_assets` are scanned graph facts, not deletion proof. They still require review for primary asset rules, localization, runtime-generated names, soft loads outside scanned mounts, and failed or unsupported evidence.

## Exit codes

Report `status` and process exit code answer different questions: `status` describes the evidence, the exit code describes whether the run itself held together. A `partial` or `unsupported` report is a successful run.

- **0** — a report was produced and nothing the scan was asked to do failed. This includes `status=partial` and `status=unsupported`.
- **2** — `project` only: a hard scan failure, meaning a mapped asset that could not be read, indexed, or parsed, a mount or cache error raised during the scan, or a `--focus` pattern that selected nothing. The report is still written, so a stale `--output` is never left behind to be read as a fresh success.
- **1** — the command could not get far enough to produce a report: the `asset` file could not be read, parsed, or is out of scope; the project could not be discovered; a `--mount` argument was malformed; the command line itself was invalid; or the output could not be written. A usage error is deliberately `1` rather than clap's default `2`, so it cannot be mistaken for a scan failure that did write a report. Instead of a report the CLI emits `{"schema_version", "status": "error", "message"}` on stderr, and to `--output` when given. `"error"` is this fatal-failure document only; it is never a value of a report's `status`.

Inherent partial or unsupported evidence — known-opaque compiled RigVM, Blueprint or Niagara bytecode, a legacy set/map tag without an inner struct name — keeps a truthful non-complete `status` and exits zero. A package whose `FileVersionUE5` lies outside the supported range is different: it is out of scope, so `asset` exits 1 with an error document while `project` indexes it as `unsupported`. `--allow-partial` downgrades a hard scan failure to a zero exit; it does not erase `status`, coverage gaps, or `failures`.
